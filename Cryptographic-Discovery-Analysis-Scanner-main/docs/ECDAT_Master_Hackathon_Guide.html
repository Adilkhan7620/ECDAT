Problem & Judging Rubric

NTRO wants a tool that inventories every cryptographic artefact across code, binaries, libraries and containers; assesses quantum risk via Mosca's algorithm; classifies assets by criticality; and recommends PQC/hybrid alternatives — delivered as a CBOM report plus an interactive GUI.

Judging weights — design every feature against this

02

Our Solution, In One Line

CBOM generation is commoditized. ECDAT is the correlation, trust, and prioritization layer on top of it, tuned to India's sovereign compliance timeline. Say this sentence in the pitch — it pre-empts the "you just wrapped open-source scanners" objection.

Tier 1 — MVP, days 1–4

Discovery + Risk Engine

  • 5 scanners (Semgrep, Gitleaks, Syft, Trivy, OpenSSL) feeding a Correlation Engine
  • Mosca risk engine with configurable threat-horizon
  • Blast Radius calculation
  • PQC recommendation engine + comparison matrix
  • Dashboard: inventory, asset detail, risk view, dependency graph
Tier 2 — stretch, days 5–6

Reachability, Compliance, Drift

  • Reachability = internet-facing × sensitive-data (combination, not tracing)
  • Policy Compliance engine against a YAML rules file
  • Drift Detection — pre-computed, demoed as a static before/after screen

The Three Differentiators That Move the Score

Ranked by novelty-per-hour of build effort. Build these before anything else in Tier 2.

~1 day

A · Ensemble Reconciliation

2026 research (BF-CBOM, ARES) shows CBOM tools disagree and miss assets independently. Show your Correlation Engine visibly reconciling conflicting scanner outputs with a per-asset detected-by-N-scanners confidence score.

~0.5 day

B · Signed, Tamper-Evident CBOM

CycloneDX natively supports JSF/JWS signing. Add a "Sign CBOM" button + live tamper-detection demo (edit one byte → verification fails). Government-grade trust story, no other team will show this.

~0.5 day

C · India-Sovereign Compliance Pack

Preload the policy engine with DST/NQM 2027–2029 CII deadlines, RBI Q-SAFE's CBOM mandate, and CNSA 2.0 — every asset gets a verdict tied to a named Indian deadline, not just a generic standard.

Secondary showmanship (reuse existing components)

D · Live Mosca timeline

Drag a Q-Day slider (2029 ↔ 2035) and watch assets flip risk color in real time — makes the risk engine the demo centerpiece instead of a static table.

E · Reachability as a graph

Fuse internet-facing + sensitive-data flags into your React Flow dependency graph so one vulnerable root lights up everything downstream it protects.

Explicitly descoped: full unknown/custom-crypto detection. It's an open research problem (data-flow graphs, symbolic execution). If time allows, add only a low-confidence "candidate custom-crypto" heuristic flag (entropy + XOR/loop density) — label it clearly, never claim it as detection.

Scan & Correlation Pipeline

The sequence that actually differentiates ECDAT — five independent scanners, one reconciled truth.

sequenceDiagram participant U as User participant API as API Gateway participant O as Orchestrator participant S as Scanners (x5) participant C as Correlation Engine participant DB as Postgres participant R as Risk Engine U->>API: POST /scans (repo url) API->>O: dispatch scan job O->>S: run in parallel (sandboxed) S-->>O: raw findings (per-tool format) O->>C: normalize + merge C->>C: dedupe, resolve conflicts,
assign confidence score C->>DB: persist unified CBOM record DB->>R: trigger risk scoring R->>R: Mosca algorithm + Blast Radius R->>DB: write quantum_risk, pqc_recommendation API-->>U: GET /assets → reconciled CBOM
Every asset record should carry a sources: ["semgrep","cbomkit-rules","binary-yara"] array — this is the visual proof of ensemble reconciliation (Differentiator A) on the asset detail screen.

Demo Script (3 minutes)

  1. Open with the thesis (20s): "CBOM generation is commoditized — the hard problem is correlation, trust, and prioritization. That's ECDAT."
  2. Live scan (40s): point at a pre-vetted repo, show the 5 scanners firing, land on the reconciled inventory with per-asset detected-by-N confidence.
  3. Risk story (40s): drag the Mosca Q-Day slider from 2035 to 2029 — watch assets flip red. Explain harvest-now-decrypt-later in one sentence.
  4. Trust + sovereignty (40s): click "Sign CBOM," then tamper one byte and show verification fail. Switch policy pack to India CII — show a real 2027 deadline attached to a real asset.
  5. Close (20s): reachability graph — one root cert lighting up everything it protects. "Fix this one thing, protect all of that."
Rehearse against the clock at least twice on Day 6 — Time Discipline is a penalty criterion, not a bonus one.

Risk & Fallback Plan

  • Live scan fails on stage: fall back to pre-cached scan results — never demo an uncached scan cold.
  • Drift Detection: both scans pre-run offline; demo loads a static before/after screen, never two live scans back to back.
  • Signing library issues: downgrade to a SHA-256 hash + detached signature — still proves tamper-evidence.
  • "Why not just use CBOMkit?" question: answer directly — CBOMkit generates a CBOM; ECDAT correlates multiple generators, signs the output, and maps it to India's own compliance timeline.
  • "How deep does reachability go?" question: be honest — it's a two-field combination (internet-facing × sensitive-data), not network tracing. Frame static analysis as the correct scope for this PS, with runtime discovery as a natural Phase 2.
